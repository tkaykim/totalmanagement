# 미해결 문제

각 항목은 조건 → 증상 → 영향 범위 → 지금 못 고치는 이유 → 접근 방향 순서로 적는다.

## 치명

### 공개 저장소의 git 기록에 테스트 계정 비밀번호가 남아 있다
- **증상**: 루트 Playwright 스크립트 11개가 과거 커밋에서 ERP 테스트 계정(관리자·재무 포함 4개)의 이메일과 비밀번호를 평문으로 담고 있었다. 2026-09-24 현재 파일에서는 값을 지우고 환경변수로 바꿨지만, 저장소가 공개라 과거 커밋에서 누구나 읽을 수 있다.
- **영향**: 비밀번호를 바꾸기 전까지는 누구나 그 계정으로 로그인해 전사 재무·거래처·직원 정보를 보고 고칠 수 있다(RLS가 `authenticated` 전권이므로).
- **지금 못 고치는 이유**: 해결은 네 계정의 비밀번호 교체뿐이고, 교체는 대표가 직접 한다. 네 계정은 ERP 테스트 전용이며 다른 서비스에서 같은 비밀번호를 쓰지 않는다(2026-09-24 대표 확인).
- **접근**: 대표가 Supabase 인증 화면에서 네 계정 비밀번호를 바꾸면 이 항목을 닫는다. git 기록 정리는 선택 사항이다.

### 운영에는 아직 권한 봉인이 반영되지 않았다 (가입자·퇴사자 전권, 서명 URL, 확정 건 삭제)
- **증상**(운영 배포본 `main` `d504793` + 봉인 전 운영 DB)
  - `/signup`으로 누구나 가입해 `authenticated` 세션을 얻고, 핵심 테이블 RLS가 `authenticated` 전권이라 전사 데이터를 읽고 쓴다. `app_users`는 비로그인 INSERT와 본인 `role` 변경을 받는다.
  - 퇴사자(6명)도 같은 세션으로 API와 PostgREST를 그대로 쓴다.
  - `GET /api/storage/signed-url`이 로그인 없이 `document-room` 서명 URL을 발급한다. 로그인 확인 없는 라우트가 24개다.
  - 매출·지출은 로그인만 하면 누구나 고치고 지운다. 프로젝트 삭제는 딸린 매출·지출을 연쇄 삭제하고, 법인카드 연결 해제·이동은 `paid` 지출 행을 지운다.
  - 크론 비밀값이 없으면 크론 5개가 공개 호출된다.
  - 뷰 2개가 소유자 권한으로 근태 RLS를 우회한다.
- **영향**: 전사 재무·거래처·직원 정보와 회사 서류가 외부인에게 노출·변조될 수 있고, 확정 금액이 기록 없이 사라질 수 있다.
- **지금 못 고치는 이유**: 수정은 작업 브랜치에 모두 구현되어 있다(서버 가드·권한표·가입 승인·서명 URL 삭제·카드 연결 보존·크론 Bearer, 봉인 SQL·되돌리기 스크립트). 운영 반영에는 대표 승인 두 번(① 코드 배포 + `CRON_SECRET` 설정, ② 봉인 SQL 적용 + `ERP_AUDIT_V2` 켜기)과, 그 사이 reactstudio.kr 봉인 대비 변경의 운영 배포가 필요하다.
- **접근**: 승인 ① → reactstudio.kr 배포 → 승인 ② 순서로 반영한다. ② 전에 reactstudio.kr 배포가 끝나지 않으면 ②를 요청하지 않는다. 반영이 끝나면 이 항목을 닫는다.

### 비로그인 누구나 회사 통장사본·사업자등록증을 내려받을 수 있다
- **증상**: `company_documents`의 읽기 정책 "company_documents read all"이 역할 지정 없는(PUBLIC) `USING (true)`라 비로그인(anon)도 전체 행을 읽는다. 행에는 통장사본·사업자등록증 파일의 `public_url`이 있고, 버킷 `company-docs`는 공개 버킷이다(2026-09-25 운영 조회, 행 2개). 익명 키는 reactstudio.kr 브라우저 번들에 들어 있다.
- **영향**: 누구나 익명 키로 PostgREST를 불러 URL을 얻고 파일을 내려받을 수 있다. 계좌·사업자 정보가 악용될 수 있다. 같은 이유로 공개 버킷 `comment-attachments`·`project-documents`의 파일도 경로만 알면 누구나 받는다.
- **지금 못 고치는 이유**: 봉인 SQL은 anon 정책을 바꾸지 않는다는 범위로 만들었다. 이 정책을 바꾸거나 버킷을 비공개로 돌리는 것은 운영 DB·Storage 변경이라 대표 승인이 필요하다. reactstudio.kr의 문서 첨부(`lib/company-docs.ts`)는 서비스 권한 키로 읽으므로 정책을 좁혀도 그쪽은 깨지지 않을 것으로 보이지만, 공개 URL을 쓰는 다른 곳이 없는지 확인해야 한다.
- **접근**: 읽기 정책을 `service_role` 전용으로 바꾸고(또는 `is_active_staff()` 조건), `company-docs` 버킷을 비공개로 바꾼 뒤 서명 URL로만 내보낸다. 되돌리기 SQL을 함께 둔다.

## 해결됨(2026-09-25 봉인 SQL 운영 적용)

### 봉인 뒤에도 가입 대기·퇴사 계정이 봉인 밖 테이블을 PostgREST로 읽고 쓴다
- **증상**: 처음 봉인 SQL은 5개 테이블(`app_users`, `projects`, `project_tasks`, `financial_entries`, `gowid_expense_project_link`)만 바꿨다. `partners`, `contracts`, `comments`, `document_room_files` 등은 `authenticated` 전권 정책이 그대로였고, `clients`는 `authenticated` 쓰기가 열려 있었다. 가입 직후 `authenticated` 세션이 생기므로 승인 전 계정과 퇴사자가 이 테이블들을 직접 읽고 쓸 수 있었다.
- **해결(준비됨)**: 봉인 SQL 7절이 봉인 5개·`react_*` 밖의 47개 테이블에서 `authenticated`·PUBLIC 정책 83개의 USING·WITH CHECK에 `is_active_staff()`를 AND로 붙이고, `clients`·`company_documents`에 로그인 계정 전용 RESTRICTIVE 정책을 더한다. 재직 직원의 결과와 anon 결과는 전과 같다(알림 anon INSERT만 막힘). `tests/db/seal-outside.test.ts`가 검증하고, 되돌리기 스크립트가 기준선 본문으로 복원한다.
- **닫음**: 2026-09-25 운영 적용, 확인 6 결과 의도한 3개(`clients` 공개 읽기, `company_documents` 공개 읽기, `push_tokens` 서비스 정책)만 남았다. 재직 직원 사이의 역할·사업부별 세부 RLS는 이 항목 범위가 아니다(`docs/tracking/status.md`).

## 높음

### 지급 방식이 비어 있는 매출·지출 행
- **증상**: 지급 방식이 비어 있는 행이 424건(취소 제외 420건)이다. 이 중 MODOO가 328건, 나머지 사업부가 92건이다.
- **영향**: 지급 방식이 비어 있으면 실지급액이 계산되지 않아 통장·세금계산서 대사와 공급가 손익이 어긋날 수 있다.
- **지금 못 고치는 이유**: 해석 규칙은 2026-09-24 대표가 확정했다. 92건에 규칙대로 지급 방식을 채우는 일은 운영 DB 쓰기라 별도 승인 후 실행한다. 규칙에 맞지 않는 행은 행 단위 판단이 필요하다.
- **접근**: 돈의 종류별 규칙으로 92건의 지급 방식을 채우고 되돌리기 SQL을 남긴다. MODOO 328건은 손익 계산에 쓰지 않으므로 그대로 둔다.

### 레포만으로는 운영 스키마를 다시 만들 수 없다
- **증상**: 운영 적용 이력은 128개인데 레포 `supabase/migrations/`에는 34개(옛 31개, 2026-08-10 운영 직접 적용분 사본 2개, 봉인 SQL)뿐이다. 2026-09-24 기준선 사본(`supabase/baseline/`)은 참고용이라 마이그레이션 이력에 등록되지 않았다. `schema_.sql`은 오래된 사본이다.
- **영향**: 레포만으로 새 환경(스테이징·복제 DB)을 만들 수 없다. 기준선 이후 운영에 직접 적용한 변경은 다시 운영을 조회해야 알 수 있다.
- **지금 못 고치는 이유**: 기준선을 이력으로 만들려면 빈 DB에서 재구성해 운영과 같은지 대조해야 한다. 비용이 드는 Supabase 복제 DB가 필요하고 대표 비용 승인이 없다. 로컬 PGlite는 테스트 대상 테이블만 검증한다.
- **접근**: 대표 비용 승인 뒤 복제 DB에 기준선 + 이후 마이그레이션을 적용해 운영과 대조하고, 기준선을 첫 마이그레이션으로 삼는다.

### 등록자 없는 옛 매출·지출 행은 관리자만 고칠 수 있다
- **증상**: `created_by`가 비어 있는 옛 행(리더 없는 사업부에서 79건)은 권한표상 관리자만 수정·취소할 수 있다. 행 사업부 리더도 못 고친다.
- **영향**: 이 행들의 기한·입금일·지급 방식 정리를 관리자 한 사람이 맡아야 한다. 데이터 품질 작업이 느려진다.
- **지금 못 고치는 이유**: 대표가 이 제약을 확인하고 받아들였다. 등록자를 채우려면 행마다 실제 등록자를 확인해야 하고, 운영 데이터 수정이라 대표 승인이 필요하다.
- **접근**: 담당 사업부별로 등록자를 확인해 `created_by`를 채우는 보정 SQL(되돌리기 포함)을 만든다.

### 사업부 탭의 프로젝트 목록과 매출·지출 합계의 사업부 기준이 다르다
- **증상**: 사업부 탭의 매출·지출·손익 집계는 **행**의 `bu_code`로 묶는다. 반면 `GET /api/projects?bu=`와 프로젝트 목록의 매출·지출 합계는 **프로젝트**의 `bu_code`로 거른다. deetz 프로젝트에 붙은 REACT 제작비 행은 REACT 탭 손익에 잡히지만, 그 프로젝트는 DEETZ 탭 목록에 있다.
- **영향**: 한 탭에서 "프로젝트 합계"와 "사업부 손익"을 비교하면 교차 사업부 행만큼 숫자가 어긋난다. 사용자가 누락이나 중복으로 오해할 수 있다.
- **지금 못 고치는 이유**: 두 기준 모두 규칙상 맞다(손익은 행 사업부, 프로젝트 소속은 프로젝트 사업부). 어느 쪽으로 표시를 맞출지는 화면 설계 결정이라 대표 확인이 필요하다.
- **접근**: 사업부 탭 프로젝트 목록에 "다른 사업부 행 포함" 표시를 붙이거나, 교차 행을 따로 보여 준다.

### 모두의 유니폼 프로젝트 454건이 '준비중'으로 쌓여 있다
- **증상**: MODOO 프로젝트 543건 중 454건이 '준비중'이다. 대부분 한 사람이 주문 단위로 만든 '유니폼제작' 건이다.
- **영향**: 진행 중 프로젝트 집계·디제스트가 부풀려진다. 주문 원장(modoo)과 이중 관리가 된다.
- **지금 못 고치는 이유**: 방향은 2026-09-24 대표가 확정했다(주문 상세는 modoo 관리자, ERP는 일 합계). 454건을 '완료'로 바꾸는 일은 운영 DB 쓰기라 되돌리기 SQL을 준비해 실행한다.
- **접근**: 기존 '준비중' MODOO 주문 프로젝트를 '완료'로 일괄 정리하고, 새 주문 프로젝트는 만들지 않는다. 일 합계 적재는 결제형 매출 일 합계 작업에서 만든다.

## 보통

### 로그아웃 상태로 `/attendance`를 열면 로그인 화면으로 가지 않는다
- **조건·증상**: 로그인 없이 `/attendance`에 들어가면 "근태 정보를 불러올 수 없습니다." 문구만 나오고, `/api/attendance/status`를 몇 초마다 401로 계속 부른다. `/leave/admin`·`/artist`·`/`는 `/login`으로 간다.
- **영향**: 데이터 노출은 없다(API가 401). 세션이 만료된 직원이 출퇴근 화면에서 원인을 모르고 헤맬 수 있다.
- **못 고친 이유**: 2026-09-25 비로그인 점검에서 발견. 운영 반영 뒤 첫 수정 묶음에 넣는다.
- **접근**: 출퇴근 페이지도 다른 페이지처럼 세션이 없으면 `/login`으로 보내고, 401이면 폴링을 멈춘다.

### 할일 설명란에 공용 메일 비밀번호가 평문으로 있다
- **증상**: 운영 `project_tasks` id 380·381의 설명란에 공용 메일 계정 비밀번호가 적혀 있다.
- **영향**: 로그인 직원 전원과, 가입 구멍을 통한 외부인이 읽을 수 있다.
- **지금 못 고치는 이유**: 운영 데이터 수정은 대표 승인이 필요하다. 비밀번호 교체는 해당 메일 계정 관리자가 해야 한다.
- **접근**: 비밀번호를 교체하고 설명란 내용을 지운다.

### reactstudio.kr 쓰기에는 관리자 전용 전이와 기한 필수가 걸리지 않는다
- **증상**: reactstudio.kr 관리 화면은 서비스 권한 키로 `financial_entries`에 직접 쓴다. DB는 행위자를 모르므로 봉인 뒤에도 그쪽에서 `paid`→`planned` 되돌리기, `canceled` 되살리기, 기한 없는 `planned` 저장이 가능하다. 걸리는 것은 삭제 금지·재무 있는 프로젝트 삭제 차단·변경 기록(출처 "외부", 변경자 없음)뿐이다.
- **영향**: REACT 지출의 확정 상태가 ERP 규칙과 다르게 바뀔 수 있고, 누가 바꿨는지는 기록에 남지 않는다.
- **지금 못 고치는 이유**: 별도 저장소라 그쪽 서버 라우트에 같은 전이 규칙을 넣어야 하고, 그 저장소의 검증·배포 승인이 따로 필요하다. 대표가 1차에서는 이 한계를 권장안으로 받아들였다.
- **접근**: reactstudio.kr 서버 라우트에 ERP와 같은 전이 판정을 넣고, 쓰기 때 `updated_by`를 채워 변경자가 남게 한다.

### 푸시 관리 라우트는 역할 판정을 라우트 안에서 직접 한다
- **증상**: `push/send`·`push/conditional`·`push/scenario`·`push/test`(POST)·`push/tokens`는 재직 가드 뒤에 쿠키 세션 클라이언트로 `app_users.role`을 다시 읽어 `admin`인지 라우트 안에서 비교한다. `permissions.ts` 판정을 쓰지 않는다.
- **영향**: 지금은 관리자만 통과해 동작상 문제는 없다. 하지만 권한 규칙이 두 곳에 있어, 판정 규칙이 바뀌면 이 라우트만 옛 규칙으로 남는다. 봉인 뒤 세션으로 `app_users`를 읽는 방식은 재직 직원에게만 전체 행이 보이므로 가드를 통과한 사용자에게는 영향이 없다.
- **지금 못 고치는 이유**: 1차 범위(가드 적용)에 판정 이관은 포함되지 않았다. 코드 변경과 운영 배포 승인이 필요하다.
- **접근**: 가드가 준 `appUser`로 `permissions.ts`에 푸시 발송 판정 함수를 두고 부른다.

### `GET /api/auth/me`가 비재직 계정에 403을 준다
- **증상**: 이 라우트에 재직 가드가 붙어 승인 대기·거절·퇴사 계정은 200 대신 403을 받는다. 이 레포 화면에는 호출하는 곳이 없다.
- **영향**: 네이티브 앱 빌드나 외부 스크립트가 이 라우트로 로그인 상태를 판단하고 있다면 비재직 계정 처리 흐름이 바뀐다.
- **지금 못 고치는 이유**: 앱 스토어 배포본과 외부 호출자의 사용 여부를 레포에서 확인할 수 없다.
- **접근**: 본인 상태가 필요한 곳은 `GET /api/users/me/status`를 쓰게 한다. 운영 반영 뒤 서버 로그에서 이 라우트의 403을 확인한다.

### 이미 틀린 사업부로 저장된 할일이 남아 있을 수 있다
- **증상**: 운영 배포본은 할일을 다른 프로젝트로 옮겨도 `project_tasks.bu_code`를 옛 프로젝트 값으로 저장했다. 작업 브랜치는 새 프로젝트 기준으로 고쳤지만 이미 저장된 행은 그대로다.
- **영향**: 사업부별 할일 집계와 과부하 탐지가 그 행만큼 틀린다.
- **지금 못 고치는 이유**: 운영 데이터 수정이라 대표 승인이 필요하다.
- **접근**: `project_tasks.bu_code <> projects.bu_code`인 행을 조회해 보정 SQL(되돌리기 포함)을 만든다.

### 연차 자동 부여와 연차 계산 함수가 다르다
- **증상**: 1월 1일 자동 부여는 15일 고정이다. `calculateAnnualLeave`는 근속 가산일(최대 +10일)을 더한다.
- **영향**: 3년차 이상 직원의 연차가 계산값보다 적게 부여되고, 화면 표시와 실제 잔여가 다를 수 있다.
- **지금 못 고치는 이유**: 가산일을 자동으로 넣을지 회사 방침이 확인되지 않았다.
- **접근**: 대표 확인 뒤 자동 부여를 계산 함수로 통일한다.
