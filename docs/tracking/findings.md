# 미해결 문제

각 항목은 조건 → 증상 → 영향 범위 → 지금 못 고치는 이유 → 접근 방향 순서로 적는다.

## 치명

### 공개 저장소에 실제 로그인 정보가 커밋되어 있다
- **증상**: 저장소는 공개다. 루트의 Playwright 스크립트에 ERP 로그인 이메일과 비밀번호 문자열이 평문으로 들어 있다.
  - 이메일과 비밀번호 입력값이 함께 있는 파일(10개): `test-admin-worklog.js`, `test-attendance-admin.js`, `test-local-template.js`, `test-manual-editor.js`, `test-manual-feature.js`, `test-manual-selector.js`, `test-template-feature.js`, `test-template-local.js`, `test-template-selector-local.js`, `test-template-selector-v2.js`
  - 계정 이메일 문자열만 있는 파일: `test-manual-simple.js`
  - 로그인 정보가 없는 파일: `test-task-navigation.js`
- **영향**: 누구나 그 계정으로 로그인해 전사 재무·거래처·직원 정보를 보고 고칠 수 있다(RLS가 `authenticated` 전권이므로). 재무 계정이 포함되어 있다.
- **지금 못 고치는 이유**: 파일에서 값을 지워도 git 기록에 남으므로, 실제 해결은 비밀번호 교체뿐이다. 교체는 각 계정 소유자(직원 본인·관리자)의 확인과 조치가 필요하다.
- **접근**: 위 파일에 나오는 이메일 계정마다 아직 쓰는 계정인지 확인하고 비밀번호를 교체한다. 파일에서는 값을 지우고 환경변수로 바꾼다. git 기록 정리는 교체 뒤 선택 사항이다.

### 누구나 가입해 전사 데이터를 읽고 쓰고, 스스로 관리자가 될 수 있다
- **증상**
  - `/signup`으로 가입하면 `authenticated` 세션이 생긴다.
  - `app_users`는 비로그인 INSERT를 역할 검사 없이 받는다.
  - 로그인 사용자는 본인 행을 포함해 `app_users` 전체를 update할 수 있다.
  - 핵심 테이블 RLS가 `authenticated` 전권이다.
- **영향**: 전사 재무·거래처·계약·직원 정보가 외부인에게 노출되고 변조될 수 있다.
- **지금 못 고치는 이유**: 가입 승인 흐름(대표 확정: 가입 후 관리자 승인)을 새로 만들어야 한다. RLS를 바꾸면 화면의 직접 조회와 reactstudio.kr 공개 페이지가 영향을 받으므로, 브랜치 DB 검증과 운영 DB 변경에 대한 대표 승인이 필요하다.
- **접근**
  - 승인 전 계정을 비활성 상태로 두고, RLS 조건을 "재직·승인된 `app_users` 존재"로 바꾼다.
  - 본인 행 update에서 `role`·`bu_code`·`status` 변경을 막는다.

### 퇴사자가 데이터에 계속 접근할 수 있다
- **증상**: `status='retired'` 계정은 메인 화면에서만 로그아웃된다. 같은 세션으로 API와 PostgREST는 그대로 쓸 수 있다.
- **영향**: 퇴사자 6명이 전사 데이터를 볼 수 있는 상태다.
- **지금 못 고치는 이유**: RLS 조건 변경(운영 DB 변경 → 대표 승인, reactstudio.kr 공개 페이지 영향 검증 필요)과 서버 공통 가드 코드 변경이 함께 필요하다. 퇴사자 Auth 계정 비활성화도 운영 계정 변경이라 대표 승인이 필요하다.
- **접근**: 서버 공통 가드와 RLS에서 `status='active'`를 확인한다. 당장은 퇴사자 Auth 계정을 비활성화(ban)하는 방법도 있다.

### 인증 없이 회사 서류 서명 URL을 받을 수 있다
- **증상**
  - `GET /api/storage/signed-url?bucket=document-room&path=...`가 로그인 확인 없이 서비스 권한 키로 서명 URL을 발급한다.
  - `upload`, `clients`, `org-members`, `channels`, `events`, `external-workers`, `client-workers`, `manuals` 등 24개 라우트 파일도 로그인 확인이 없다.
  - Gowid 라우트는 공용 `requireAuth`로 확인하므로 여기에 포함되지 않는다.
- **영향**: 경로를 알거나 추측할 수 있으면 사업자등록증·통장사본을 받을 수 있다. 거래처·조직·외부 인력 목록을 비로그인으로 조회·수정할 수 있다.
- **지금 못 고치는 이유**: 약 24개 라우트에 공통 가드를 넣는 코드 변경이고, 화면이 이 라우트를 로그인 상태로만 부르는지 라우트별 확인과 운영 배포 승인이 필요하다.
- **접근**: 공통 `requireUser`·`requireRole`을 만들어 전 라우트에 적용한다.

### 매출·지출을 누구나 수정·삭제할 수 있고, 지급 완료 건도 지워진다
- **증상**
  - `PATCH/DELETE /api/financial-entries/[id]`는 로그인만 확인한다. 요청 본문을 그대로 서버 권한 키 update에 넘긴다.
  - 프로젝트 삭제는 딸린 매출·지출을 연쇄 삭제한다.
  - 법인카드 연결 해제·이동은 `paid` 지출 행을 지운다.
  - reactstudio.kr 관리 API도 REACT 지출을 권한 규칙 없이 수정·삭제한다.
- **영향**: 대표 확정 규칙(수정은 본인·사업부 리더·관리자, `paid`·`canceled` 삭제 금지, 되돌리기는 관리자만, 변경 기록)이 전혀 강제되지 않는다. 금액·상태·사업부가 기록 없이 바뀔 수 있다.
- **지금 못 고치는 이유**: DB 트리거 추가는 운영 DB 변경이라 대표 승인이 필요하다. reactstudio는 별도 레포라 함께 바꿔야 한다. 삭제 금지를 프로젝트 삭제·카드 연결 변경·reactstudio 경로에 어떻게 적용할지 대표 확인이 필요하다.
- **접근**
  - DB 트리거로 `paid`·`canceled` 삭제를 거부하고 변경 기록을 남긴다. 그러면 모든 쓰기 경로에 한 번에 걸린다.
  - 서버 라우트에는 역할 판정과 허용 컬럼을 넣는다.

## 높음

### 지급 방식이 비어 있는 매출·지출 행
- **증상**: 지급 방식이 비어 있는 행이 424건(취소 제외 420건)이다. 이 중 MODOO가 328건, 나머지 사업부가 92건이다.
- **영향**: 지급 방식이 비어 있으면 실지급액이 계산되지 않아 통장·세금계산서 대사와 공급가 손익이 어긋날 수 있다.
- **지금 못 고치는 이유**: 해석 규칙은 2026-09-24 대표가 확정했다. 92건에 규칙대로 지급 방식을 채우는 일은 운영 DB 쓰기라 별도 승인 후 실행한다. 규칙에 맞지 않는 행은 행 단위 판단이 필요하다.
- **접근**: 돈의 종류별 규칙으로 92건의 지급 방식을 채우고 되돌리기 SQL을 남긴다. MODOO 328건은 손익 계산에 쓰지 않으므로 그대로 둔다.

### 화면에서 매출·지출 기한·입금일을 입력할 수 없다
- **증상**: 운영 화면의 매출·지출 입력 모달과 `POST /api/financial-entries`는 `due_date`·`paid_at`을 다루지 않는다.
- **영향**: "완료 전에 받을 돈을 `planned` + `due_date`로 등록한다"는 운영 원칙을 화면으로 지킬 수 없다. 미수금·미지급 계산(기한 기준)과 워커 디제스트의 기한 누락 경보가 계속 쌓인다.
- **지금 못 고치는 이유**: 기한 입력·검증 구현은 미검증 브랜치(`feature/financial-entry-due-date-validation`, 보관 브랜치에도 포함)에 있다. 반영하려면 그 브랜치를 검증하고 운영 배포 승인을 받아야 한다.
- **접근**: 해당 브랜치를 검증해 반영하면서 `paid` 전환 시 `paid_at` 입력도 함께 넣는다.

### 운영 코드가 DEETZ와 내부배부를 모른다
- **증상**: 운영 DB에 DEETZ 사업부(프로젝트 10건)와 `entry_scope`가 있다. main 코드는 사업부 목록 30여 곳이 6개로 고정되어 있고, 화면 손익은 내부배부 3건을 외부 거래처럼 더한다.
- **영향**: DEETZ 프로젝트가 사업부 탭·필터·권한 판정에서 빠진다. 화면의 사업부 손익이 워커의 월 손익과 다르게 나온다.
- **지금 못 고치는 이유**: 해당 화면 코드는 검증 전 보관 브랜치(`wip/deetz-crossbu-accounting-ui-20260924`, push 안 됨)에 있다. 반영하려면 브랜치 검증과 운영 배포 승인이 필요하다.
- **접근**: 보관 브랜치를 검증해 반영하고, 사업부 목록을 한 곳 정의로 모은다.

### 운영 DB와 레포 마이그레이션이 크게 어긋난다
- **증상**: 운영 적용 이력은 약 130개인데 레포에는 31개뿐이다. `schema_.sql`과 `src/types/database.ts`도 운영보다 뒤처져 있다.
- **영향**: 레포만 보고 스키마를 판단하거나 새 환경을 만들면 틀린다.
- **지금 못 고치는 이유**: 운영 스키마 전체를 덤프해 기준선 파일을 만들고, 그 파일로 빈 DB를 재구성해 운영과 같은지 대조해야 한다. 문서 작업만으로는 할 수 없다.
- **접근**: 운영 스키마를 기준선 마이그레이션 하나로 떠서 레포에 넣고, 이후 변경만 쌓는다.

### SECURITY DEFINER 뷰 2개
- **증상**: `attendance_logs_with_user`, `project_pnl_reports_with_profit`가 뷰 소유자 권한으로 실행된다.
- **영향**: 근태 RLS(본인·같은 사업부 관리자만)를 우회해 전 직원 근태를 읽을 수 있다.
- **지금 못 고치는 이유**: 뷰 정의 변경은 운영 DB 변경이라 대표 승인이 필요하다. 워커·화면이 이 뷰로 다른 사람 근태를 읽는 곳이 있는지도 먼저 확인해야 한다.
- **접근**: `security_invoker=true`로 바꾼다.

### 모두의 유니폼 프로젝트 454건이 '준비중'으로 쌓여 있다
- **증상**: MODOO 프로젝트 543건 중 454건이 '준비중'이다. 대부분 한 사람이 주문 단위로 만든 '유니폼제작' 건이다.
- **영향**: 진행 중 프로젝트 집계·디제스트가 부풀려진다. 주문 원장(modoo)과 이중 관리가 된다.
- **지금 못 고치는 이유**: 방향은 2026-09-24 대표가 확정했다(주문 상세는 modoo 관리자, ERP는 일 합계). 454건을 '완료'로 바꾸는 일은 운영 DB 쓰기라 되돌리기 SQL을 준비해 실행한다.
- **접근**: 기존 '준비중' MODOO 주문 프로젝트를 '완료'로 일괄 정리하고, 새 주문 프로젝트는 만들지 않는다. 일 합계 적재는 결제형 매출 일 합계 작업에서 만든다.

## 보통

### 할일 설명란에 공용 메일 비밀번호가 평문으로 있다
- **증상**: 운영 `project_tasks` id 380·381의 설명란에 공용 메일 계정 비밀번호가 적혀 있다.
- **영향**: 로그인 직원 전원과, 가입 구멍을 통한 외부인이 읽을 수 있다.
- **지금 못 고치는 이유**: 운영 데이터 수정은 대표 승인이 필요하다. 비밀번호 교체는 해당 메일 계정 관리자가 해야 한다.
- **접근**: 비밀번호를 교체하고 설명란 내용을 지운다.

### 크론 비밀값이 없으면 크론 라우트가 공개된다
- **증상**
  - 크론 5개 라우트는 `CRON_SECRET`이 없으면 확인을 건너뛴다.
  - 로컬 설정에는 값이 없고, 운영 설정 여부는 확인되지 않았다.
  - 알림 크론은 쿼리 키 방식이라, 값을 설정하면 키 없는 `vercel.json` 호출이 401로 실패한다.
- **영향**: 누구나 강제 퇴근·연차 부여·알림 발송을 호출할 수 있다. 알림 크론은 중복 확인이 없어 반복 호출하면 알림이 폭주한다.
- **지금 못 고치는 이유**: 운영 Vercel 환경변수를 확인·설정할 권한과 승인이 필요하다. 알림 크론 인증 방식을 바꾸는 코드 변경과 동시에 배포해야 크론이 끊기지 않는다.
- **접근**: 크론을 모두 `Authorization: Bearer` 방식으로 통일한 뒤 `CRON_SECRET`을 설정한다.

### 할일을 다른 프로젝트로 옮기면 사업부가 옛 값으로 남는다
- **증상**: `PATCH /api/tasks/[id]`에 `project_id`를 보내면 `bu_code`가 옮기기 전 프로젝트 값으로 저장된다.
- **영향**: 사업부별 할일 집계와 과부하 탐지가 틀린다.
- **지금 못 고치는 이유**: 같은 라우트의 `...body` 정리와 함께 고치는 편이 안전하다. 코드 변경과 운영 배포 승인이 필요하다. 이미 틀린 사업부로 저장된 할일의 보정은 운영 데이터 수정이라 대표 승인이 필요하다.
- **접근**: 새 `project_id`의 프로젝트에서 `bu_code`를 읽는다.

### 연차 자동 부여와 연차 계산 함수가 다르다
- **증상**: 1월 1일 자동 부여는 15일 고정이다. `calculateAnnualLeave`는 근속 가산일(최대 +10일)을 더한다.
- **영향**: 3년차 이상 직원의 연차가 계산값보다 적게 부여되고, 화면 표시와 실제 잔여가 다를 수 있다.
- **지금 못 고치는 이유**: 가산일을 자동으로 넣을지 회사 방침이 확인되지 않았다.
- **접근**: 대표 확인 뒤 자동 부여를 계산 함수로 통일한다.
